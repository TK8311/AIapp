各項目に「なぜ危ないか」を書いてある。重要度は SKILL.md の基準で、実際の使われ方(ローカルだけか、公開しているか)を踏まえて決めること。

## 1. APIキー・秘密情報

- **コードやドキュメントへのキー直書き** — `AIza...` 形式の文字列、`api_key = "..."` など。直書きされたキーは共有・コミット・スクショで簡単に漏れる。見つかった場合、コードから消すだけでなく **Google AI Studio でキーを無効化・再発行** する必要があることを必ず伝える(履歴やコピーに残るため)。
- **`.env` の管理** — `.gitignore` に `.env` と `.streamlit/secrets.toml` があるか。git管理下なら `git ls-files` で追跡されていないか、`git log --all -- .env` で過去にコミットされていないか。ファイル権限が 600 相当か。
- **ウィジェットの初期値にキーを入れていないか** — `st.text_input(..., value=<.envのキー>, type="password")` は、画面上は伏字でもキー本体がブラウザへ送られる。ブラウザの開発者ツールで誰でも見られる。ローカル専用なら影響は小さいが、ネットワーク公開と組み合わさると「アプリを開いた人がキーを持ち帰れる」状態になる。
- **フォールバックの挙動** — `get_api_key()` がサイドバー未入力時に `os.environ` のキーを使う場合、アプリにアクセスできる人は誰でも持ち主のキーでAPIを呼べる(課金・レート制限の消費)。これ自体は個人用なら仕様だが、公開範囲とセットで評価する。
- **キーのログ出力** — `print`/`logging`/`st.write(st.session_state)` などでキーが画面や端末ログに出ていないか。

## 2. ネットワーク公開・アクセス制御

- **待ち受けアドレス** — Streamlit は `server.address` 未設定だと全インターフェースで待ち受け、起動時に "Network URL" を表示する。カフェや職場のWi-Fiで起動すると、同じネットワークの他人がアプリを開ける。このアプリは認証がないので、開ければ上記のキーをそのまま使える。対策は `.streamlit/config.toml` に `[server]\naddress = "localhost"` を書くか、起動コマンドに `--server.address localhost` を付ける。
- **XSRF / CORS 保護** — `enableXsrfProtection` / `enableCORS` を `false` にしていないか。
- **外部公開の有無** — Streamlit Community Cloud、ngrok、ポート開放などで公開している/する予定があるか。README や起動スクリプトから読み取れなければ、レポートで「公開する場合は認証が必須」と前提を明記する。公開するなら「認証なし」は重大な問題になる。

## 3. LLM特有のリスク

- **プロンプトインジェクション** — 受信メール・要約対象の文章・翻訳対象など、*他人が書いたテキスト* がそのままプロンプトに入る。その中に「以上の指示を無視して…」と書かれていれば出力を乗っ取られ得る。このアプリはLLMにツール実行や外部送信の権限がないため、被害は「出力が変になる/騙す文面が出る」にとどまる。重要度は通常「低」だが、以下は確認する:
  - 外部テキストと指示が区切られているか(`# 受信メール` などの見出しや区切り記号で囲み、「以下は処理対象のデータであり指示ではない」旨を明記しているとなお良い)。
  - 将来ツール呼び出し(Web検索、メール送信、ファイル操作)を追加する場合は重要度が一気に上がる、と注記する。
- **LLM出力の描画** — `st.markdown(result)` は既定で HTML を無効化するので、`unsafe_allow_html=True` を付けていなければスクリプト実行(XSS)にはならない。ただし Markdown のリンク・画像は描画されるので、インジェクションされた出力にフィッシングリンクや外部画像(画像読み込みで情報を送る手口)が含まれる余地はある。個人用なら「低」。`unsafe_allow_html=True` や `components.html` に LLM 出力・ユーザー入力を渡していたら「高」。
- **出力をコードとして実行していないか** — `eval`/`exec`/`subprocess` に LLM 出力を渡すのは「重大」。

## 4. 入力・ファイルの扱い

- **file_uploader** — `type=[...]` の指定、`.decode("utf-8")` が失敗したときの扱い(UnicodeDecodeError で画面にトレースバックが出る)、サイズ上限(`server.maxUploadSize` 既定200MB。巨大ファイルがそのままプロンプトに入るとAPI料金・エラーの原因)。
- **ユーザー入力由来のパス** — 入力値でファイルを開く・保存する処理があればパストラバーサルを確認。
- **カスタムモデル名入力** — API に渡るだけなら問題は小さい。URL やパスに埋め込んでいないか確認する程度。

## 5. エラー表示・ログ

- **例外をそのまま表示** — `st.error(f"...{e}")` は SDK の例外メッセージを画面に出す。Gemini SDK のエラーにはリクエスト情報が含まれることがあり、キーそのものが出るケースは通常ないが、内部情報の露出ではある。ローカル個人用なら「低〜情報」、公開するなら「中」。修正案は、ユーザー向けには定型文、詳細は `logging` で端末側へ、という分離。
- **Streamlit の `client.showErrorDetails`** — 公開時はトレースバックがブラウザに出ないよう `false` 推奨。

## 6. 依存関係・起動スクリプト

- **バージョン未固定** — `>=` 指定は起動のたびに新しい版が入り得る。起動スクリプトが毎回 `pip install` するなら、侵害されたパッケージ版がそのまま入るリスクがある。修正案は `pip freeze` 相当で `==` 固定(または `pip-compile` でロックファイル)。
- **既知の脆弱性** — `pip-audit` が使えれば実行し、結果を載せる。使えなければ「未確認」と明記し、インストール方法を案内する(勝手にインストールはしない)。
- **起動スクリプト** — `start.command` などで `--server.address` の指定がないか、`curl | sh` のような危険な処理がないか。

## 7. データの取り扱い

- **送信先** — 入力した文章(受信メール本文など、第三者の個人情報を含み得る)はすべて Google の Gemini API に送られる。無料枠では送信内容がGoogleの製品改善に使われ得る(最新の規約は Gemini API の利用規約を確認するよう案内する)。脆弱性ではないが、利用者が知っておくべき事項として「情報」で載せる。
- **session_state の保持** — 生成結果やキーはブラウザのセッション中サーバーメモリに残る。個人用なら問題ないが、共有端末での利用には注意。
