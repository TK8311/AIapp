# アプリのセキュリティチェック

このアプリは「認証なし・DBなし・個人用」の Streamlit マルチページアプリで、Gemini API キーを使う。守るべき一番の資産は **APIキー(=持ち主のお金と利用枠)** と **入力される文章(受信メールなど第三者の情報を含む)** である。チェックはこの2つがどう漏れ得るかを中心に考える。

一般的なWebアプリのチェックリストをそのまま当てはめると、「SQLインジェクション」のように存在しない問題を並べたり、個人がローカルで使うだけのアプリに「認証がない:重大」と書いてしまったりして、本当に直すべき点が埋もれる。実際の使われ方に合わせて重要度を決めることが、このスキルでいちばん大事な点。

## 手順

### 1. 前提を把握する

`CLAUDE.md`、`README.md`、起動スクリプト(`start.command` など)、`.streamlit/` の有無を見て、次の点を読み取る。

- ローカル専用か、外部公開(Streamlit Cloud・ngrok・ポート開放など)しているか、その予定があるか
- APIキーの渡し方(`.env` / サイドバー入力 / secrets.toml)

読み取れなければユーザーに聞かずに「ローカル個人利用」を前提として進め、レポートの冒頭にその前提を書く。公開する場合に重要度が上がる項目は、その旨を項目ごとに添える。

### 2. 一次スキャンを実行する

```bash
python3 <このスキルのディレクトリ>/scripts/scan.py <プロジェクトルート>
```

キーの直書き、`.gitignore`、`.env` の権限、危険な関数、`server.address`、依存関係のバージョン固定、(入っていれば)`pip-audit` を機械的に拾う。出てくるのはあくまで**候補**で、誤検知も見落としもある。候補ごとに該当コードを読んで、本当に問題かどうかを判断する。

### 3. コードを読んで確認する

`references/checklist.md` の観点に沿って、`Home.py`、`utils/*.py`、`pages/*.py` をすべて読む(ファイル数は少ないので全部読める)。特に次の点は、スキャンでは判断できず、コードの流れを追う必要がある。

- APIキーがどこから来て、どこへ流れるか(`get_api_key()` のフォールバック、ウィジェットの初期値、session_state、エラーメッセージ)
- 外部テキスト(メール本文・要約対象・アップロードファイル)がプロンプトにどう埋め込まれ、LLM出力がどう描画されるか
- ネットワーク公開と認証なしが組み合わさったときに、第三者に何ができてしまうか

同じパターンが全ページにある場合(例:7ページすべての `st.error(f"...{e}")`)は、1つの指摘にまとめて該当箇所を列挙する。7件に分けるとレポートが読みにくくなる。

### 4. 重要度を付ける

| 重要度 | 基準 |
|---|---|
| 重大 | 今の使い方のままで、キーや個人情報が第三者に渡る/任意コードが実行される(例:キーの直書き・コミット、LLM出力の `eval`) |
| 高 | 起こりやすい条件(同じWi-Fi、うっかり公開)で、キー流用や情報漏洩につながる |
| 中 | 公開した場合に問題になる、または悪用に複数の条件が必要 |
| 低 | 影響が小さい/個人ローカル利用ではほぼ問題にならない |
| 情報 | 脆弱性ではないが知っておくべきこと(データ送信先、未実施のチェックなど) |

迷ったときは「この問題で、持ち主以外の誰が、何を得られるか」を具体的に書いてみる。書けなければ重要度を下げる。

### 5. レポートを書く

プロジェクトルートに `security-report.md` を書き出す(既にあれば上書きしてよい。日付が入るので履歴の区別はつく)。読み手はプログラミング初心者の可能性があるので、専門用語には一言説明を添える。

```markdown
# セキュリティチェックレポート

- 実施日: YYYY-MM-DD
- 対象: <プロジェクトのパス>
- 前提: <ローカル個人利用 / 外部公開あり など、手順1で判断した内容>

## サマリー

| 重要度 | 件数 |
|---|---|
| 重大 | n |
| 高 | n |
| 中 | n |
| 低 | n |
| 情報 | n |

<全体の所感を2〜3文。まず何を直すべきか>

## 指摘事項

### [高] <短いタイトル>

- **場所**: `utils/sidebar.py:14`(複数あれば列挙)
- **内容**: 何が起きているか
- **想定される被害**: 誰が、どうやって、何を得られるか
- **修正案**:
  ```python
  # 修正後のコード例(差分がわかるように)
  ```
- **補足**: 公開時に重要度が変わる場合など(任意)

(重要度の高い順に並べる)

## 問題がなかった項目

- 確認して問題がなかった観点を箇条書き(例:APIキーの直書きなし、.env は gitignore 済み)

## 実施できなかったチェック

- 例:pip-audit 未インストールのため依存関係の既知脆弱性は未確認
```

「問題がなかった項目」も書くこと。何を見て大丈夫だったのかがわかると、ユーザーは安心できるし、見落としにも気づきやすくなる。

### 6. 報告して、修正は承認を待つ

チャットでは、サマリー表と重大・高の指摘を短く伝え、レポートのパスを示す。そのうえで「どの修正を適用しますか?」と聞く。**コードの修正は、ユーザーが選んだものだけを、承認を得てから行う。** セキュリティ修正は挙動を変えることがあり(例:`server.address = "localhost"` にするとスマホから開けなくなる)、何を優先するかは持ち主が決めることだから。

修正を適用したら `python3 -m py_compile Home.py utils/*.py pages/*.py` で構文を確認し、レポートの該当項目に「対応済み」と追記する。

## 注意

- APIキーそのものをレポートやチャットに書き写さない。見つけたら先頭数文字だけ残して伏字にする。
- `.env` の中身は、キーが入っていることの確認以上に読み上げない。
- キーの漏洩が疑われる場合(コミット済み、公開リポジトリにある、など)は、コードの修正だけでは不十分で、Google AI Studio でキーを無効化・再発行する必要があることを必ず伝える。
- `pip-audit` などのツールを勝手にインストールしない。未実施として記録し、方法を案内する。
